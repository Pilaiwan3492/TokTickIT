# Lab 2 Sprint Engineering Specification: TokTickIT Requester MVP

## 1. Sprint Goal
Deliver the TokTickIT MVP system for Requesters to create, inspect, and manage IT support tickets along with supporting attachments under a Spec-Driven Development architecture and Zen Green UI theme, utilizing a Development Requester Selector to simulate user context prior to authentication integration in Lab 3.

## 2. Stakeholder Request Interpretation
The IT department requires an accessible and responsive ticketing experience across all devices. Requesters must be able to specify category, description, related system, priority, and attach supporting evidence. Upon successful creation, the system automatically generates an official Ticket Number. Requesters can search, filter, sort, view details of their own tickets, and manage attachments (Upload/Soft Remove) with strict backend ownership checks preventing cross-user ticket access.

## 3. Scope
### Included
- **Development Requester Selection Screen**: Simulates user selection for testing purposes.
- **Create Ticket Workflow**: IT ticket creation form with client/server validation rules.
- **My Tickets Workflow**: Personal ticket list with Search, Filter, Sort, and Pagination capabilities.
- **Ticket Detail View**: Read-only ticket details view and attachment management.
- **Attachment Lifecycle**: File upload, download, and soft removal with reason recording.
- **Ownership Protection**: Backend enforcement restricting ticket and attachment access exclusively to the selected Requester.
- **Zen Green UI Foundation**: Reusable form, list, badge, validation, loading, empty, error, and responsive-layout conventions.

### Excluded
- Real Authentication/Authorization mechanisms (e.g., passwords, JWT, sessions).
- IT Staff Workflows (claiming/reassigning tickets, status changes, adjusting IT Priority).
- Public Comments, Internal Notes, and Actions Taken.
- Ticket status transitions beyond the initial `New` status.
- Administration functions for managing users, Requesters, roles, or reference data.

## 4. Functional Requirements
- **FR-01**: The system shall allow users to select an active Development Requester to establish the user context for testing.
- **FR-02**: The system shall support creating IT support tickets by capturing Category, Related System, Ticket Summary, Requested Priority, and Description, followed by an optional sequential attachment upload step.
- **FR-03**: The system shall generate a unique Ticket Number from the backend upon successful ticket creation.
- **FR-04**: The system shall display only tickets belonging to the currently selected Requester on the My Tickets page.
- **FR-05**: The system shall support Search, Filter, Sort, and Pagination on the My Tickets page.
- **FR-06**: The system shall display read-only ticket details and attached active/removed files on the Ticket Detail page.
- **FR-07**: The system shall allow adding permitted attachments to an existing ticket.
- **FR-08**: The system shall support soft removal of attachments by retaining metadata while disabling download and preview access.
- **FR-09**: The system shall provide master data endpoints to load active Categories and Related Systems.
- **FR-10**: The system shall reload requester-specific data whenever the selected Development Requester changes.
- **FR-11**: The backend shall enforce ownership checks for ticket and attachment operations using the currently selected Development Requester context.
- **FR-12**: The system shall provide clear loading, validation, success, empty, no-results, and failure states for the required workflows.

## 5. Business Rules
- **BR-01**: The official Ticket Number is generated by the backend in the format `TKT-YYYY-XXXXXX` and must be unique. This format is selected to provide a human-readable identifier while maintaining uniqueness through backend generation.
- **BR-02**: A newly created ticket always begins with initial Current Status `New`.
- **BR-03**: The Development Requester Selector is strictly a testing mechanism for Lab 2 and does not represent real authentication.
- **BR-04**: Requesters can only view, search, and manage tickets and attachments they own, where `requesterId` matches the currently selected Development Requester.
- **BR-05**: Ownership checks for ticket and attachment access must be enforced by the backend. Frontend filtering alone must not be considered an authorization control.
- **BR-06**: Allowed attachment file types are strictly JPG, JPEG, PNG, WEBP, and PDF, with a maximum size of 5 MB per file.
- **BR-07**: A single ticket can contain a maximum of 5 active attachments.
- **BR-08**: Attachment deletion must use soft removal by setting `removedAt` and `removalReason`. Metadata remains visible, but removed files cannot be downloaded or previewed.
- **BR-09**: Inactive Requesters must not appear in the Development Requester Selector dropdown.
- **BR-10**: Ticket Summary is required and must contain 5–150 characters after trimming leading and trailing whitespace.
- **BR-11**: Description is required and must contain 10–2,000 characters after trimming leading and trailing whitespace.
- **BR-12**: Validation rules must be enforced on both frontend and backend. Backend validation is authoritative.
- **BR-13**: The system must prevent duplicate ticket submissions while a valid submission request is being processed.
- **BR-14**: In case of ticket submission or attachment upload failure, the current form inputs and selected Requester context must be retained to avoid unnecessary data re-entry.
- **BR-15**: Uploaded filenames must be sanitized before storage and must not allow path traversal or unsafe filesystem paths.
- **BR-16**: Attachment metadata must include the original file name, file size, MIME type, storage path, upload timestamp, and removal information when applicable.
- **BR-17**: If an attachment upload fails after a ticket has already been successfully created, the ticket remains saved and the UI must clearly report the attachment failure without requiring the Requester to recreate the ticket.
- **BR-18**: Only the owner of a ticket may add or soft-remove attachments belonging to that ticket.
- **BR-19**: A removed attachment remains visible as metadata but cannot be downloaded or previewed.
- **BR-20**: The selected Development Requester ID shall be stored in client-side local memory or LocalStorage for the duration of the Lab 2 testing context.
- **BR-21**: When the selected Development Requester changes, the application must persist the new requester context and reload requester-specific ticket data.
- **BR-22**: If no Development Requester is selected, protected ticket screens must redirect the user to the Development Requester Selection screen.
- **BR-23**: If no active Requesters exist, the Development Requester Selection screen must display a clear empty state and prevent continuation.
- **BR-24**: If loading the Development Requester list or reference data fails, the UI must display a safe error message without exposing internal server details.
- **BR-25**: The system must render clear empty states when a Requester has no tickets and clear no-results states when search or filter queries return no matching tickets.
- **BR-26**: Ticket list sorting must use a deterministic secondary sort to ensure stable results when multiple tickets have the same primary sort value.

## 6. UI Specification Summary
The application shall use the Zen Green Theme with:
- **Primary Color**: `#006B3C`
- **Active Accent**: `#0B7A46`
- **Pale Emphasis**: `#EAF6EF`
- **Page Background**: `#F5F7F6`

Forms shall provide a clear visual distinction between Read-only fields and Editable fields. Error messages shall appear directly below the associated input using dark red text and border styling.

The application shall provide:
- TokTickIT application identity.
- My Tickets navigation.
- Create Ticket navigation.
- Current Development Requester display.
- Change Requester action.
- Clear active-page indication.
- Responsive mobile navigation.
- Loading, validation, submitting, success, failure, empty, and no-results states.
- Visible focus indicators for keyboard users.
- Accessible labels for icon-only controls.
- Disabled controls that cannot be activated.
- Submit buttons that enter a busy/loading state and become disabled during API processing.
- A confirmation modal with a mandatory removal reason when soft-removing an attachment.

### Responsive Behavior
- **Desktop (≥ 992 px)**: Multi-column layout with centered content and sensible maximum width.
- **Tablet (768–991 px)**: Two-column layout where practical.
- **Mobile (< 768 px)**: Vertically stacked fields and touch-friendly controls with no horizontal page scrolling.

The complete visual rules are defined in `docs/lab-02/ui-spec.md`.

## 7. Data Changes
### Prisma Data Model (PostgreSQL)
- `RequesterUser`: `id` (Int PK), `name` (String), `email` (String Unique), `isActive` (Boolean default true), `createdAt`
- `Category`: `id` (Int PK), `name` (String Unique), `isActive` (Boolean)
- `RelatedSystem`: `id` (Int PK), `name` (String Unique), `isActive` (Boolean)
- `Ticket`: `id` (UUID PK), `ticketNo` (String Unique), `requesterId` (FK -> RequesterUser), `categoryId` (FK -> Category), `relatedSystemId` (FK -> RelatedSystem), `summary` (String), `description` (Text), `requestedPriority` (Enum: LOW, MEDIUM, HIGH), `itPriority` (Enum Nullable), `currentStatus` (Enum: NEW, IN_PROGRESS, RESOLVED, CLOSED, default NEW), `createdAt`, `updatedAt`
- `Attachment`: `id` (UUID PK), `ticketId` (FK -> Ticket), `fileName` (String), `fileSize` (Int), `mimeType` (String), `filePath` (String), `uploadedAt`, `removedAt` (DateTime Nullable), `removalReason` (String Nullable)

### Indexing & Schema Justification Decision
- Create a composite index on `Ticket(requesterId, createdAt DESC)` to optimize the common My Tickets query that retrieves tickets for the selected Requester ordered by creation date.
- Create a single index on `Ticket(currentStatus)` to support status filtering.
- Use PostgreSQL UUID for Ticket and Attachment identifiers to provide non-sequential resource identifiers and support data scalability.
- Foreign keys shall enforce the required Requester, Category, Related System, and Ticket relationships.
- Soft removal shall be represented using nullable `removedAt` and `removalReason` fields.
- The schema shall remain compatible with Lab 3 authentication by allowing the future authenticated identity to map to the existing `RequesterUser` record without redesigning the Ticket ownership relationship.

## 8. API Contract Summary
### Endpoints
- `GET /api/v1/requesters/active`: Retrieve active Requesters.
- `GET /api/v1/categories`: Retrieve active Ticket Categories.
- `GET /api/v1/related-systems`: Retrieve active Related Systems.
- `POST /api/v1/tickets`: Create a new ticket.
- `GET /api/v1/tickets`: Retrieve ticket list for the selected Requester with query parameters (`search`, `categoryId`, `priority`, `status`, `page`, `limit`, `sort`).
- `GET /api/v1/tickets/:id`: Retrieve ticket details by ID (including attached files metadata) with ownership enforcement.
- `POST /api/v1/tickets/:id/attachments`: Upload an attachment with ownership enforcement.
- `GET /api/v1/attachments/:id/download`: Download an active attachment file with ownership and removal checks.
- `DELETE /api/v1/attachments/:id`: Soft remove an attachment with ownership enforcement.

### API Behavior
All API contracts shall define request and response shapes, validation behavior, ownership checks, missing-resource behavior, safe errors, pagination metadata, and HTTP status codes in `docs/lab-02/api-spec.md`.

Expected status codes include:
- `200 OK`: Successful retrieval or update.
- `201 Created`: Successful ticket or attachment creation.
- `400 Bad Request`: Invalid request data or query parameters.
- `403 Forbidden`: Resource exists but belongs to a different selected Requester.
- `404 Not Found`: Requested resource does not exist.
- `409 Conflict`: Duplicate or conflicting resource operation.
- `413 Payload Too Large`: Attachment exceeds the 5 MB limit.
- `415 Unsupported Media Type`: Attachment type is not permitted.
- `500 Internal Server Error`: Unexpected server-side failure without exposing internal details.

### Ticket List Query Contract
The ticket-list API shall support:
- Search.
- Category filtering.
- Requested priority filtering.
- Current status filtering.
- Sorting.
- Pagination.

The final parameter names, permitted values, default sorting, secondary sorting, page numbering, page-size limits, invalid-parameter behavior, and pagination response metadata shall be defined in `docs/lab-02/api-spec.md`.
The API must apply the selected Requester ownership constraint before returning ticket-list results.

## 9. Acceptance Criteria
- **AC-01**: Given valid ticket data, when the Requester submits the form, then the system saves the ticket, returns a unique Ticket Number, and displays a success state.
- **AC-02**: Given no Development Requester is selected, when the user attempts to access My Tickets, then the system redirects to the Development Requester Selection screen.
- **AC-03**: Given Requester B is selected, when attempting to access a ticket belonging to Requester A, then the backend rejects the request with HTTP 403 Forbidden.
- **AC-04**: Given an attachment is of type EXE or exceeds 5 MB, when uploaded, then the system rejects it and displays an appropriate error message.
- **AC-05**: Given an attachment has been soft-removed, when a user attempts to download it, then the system prevents the download.
- **AC-06**: Given a user searches by keyword or filters by category on My Tickets, when the request is submitted, then only matching tickets owned by the selected Requester are returned.
- **AC-07**: Given a ticket already contains 5 active attachments, when uploading an additional attachment, then the system blocks the upload.
- **AC-08**: Given the user changes the active Development Requester context, when accessing My Tickets, then the application reloads and displays only the new Requester's tickets.
- **AC-09**: Given an invalid Summary or Description, when the user submits the form, then field-level validation messages are displayed and the API is not called.
- **AC-10**: Given valid tickets span multiple pages, when the user changes page, then the API returns the correct page and pagination metadata.
- **AC-11**: Given the user selects a supported sorting option, when the list is loaded, then tickets are returned in the requested order with deterministic secondary sorting.
- **AC-12**: Given a Requester has no tickets, when My Tickets loads, then a meaningful empty state is displayed.
- **AC-13**: Given a search or filter returns no matching tickets, when the results are displayed, then a clear no-results state is shown.
- **AC-14**: Given the ticket-list or reference-data API fails, when the user loads the screen, then a safe failure state is displayed without exposing internal server details.
- **AC-15**: Given ticket creation or attachment upload fails, then the current form values and selected Requester context are retained.
- **AC-16**: Given a Requester attempts to access another Requester's attachment directly, then the backend rejects the operation according to the documented ownership policy.
- **AC-17**: Given the user soft-removes an attachment, when a removal reason is not provided, then the system prevents removal and displays a validation message.
- **AC-18**: Given the application is displayed at desktop, tablet, and mobile viewport sizes, then all required controls remain usable without clipped content, overlapping elements, or unintended horizontal scrolling.
- **AC-19**: Given a keyboard-only user navigates the application, then required controls are reachable, labels are accessible, and visible focus indicators are provided.
- **AC-20**: Given the user submits a valid ticket, then the Submit button enters a busy state and prevents duplicate submission until the API request completes.

## 11. Assumptions and Decisions
- Client state uses Local Memory / LocalStorage to maintain `selectedRequesterId` context in Lab 2.
- The Development Requester Selector is a temporary testing mechanism and will be replaced or integrated with real authentication in Lab 3.
- Ticket creation (`POST /api/v1/tickets`) and attachment upload (`POST /api/v1/tickets/:id/attachments`) represent a continuous two-step workflow executed as distinct API operations to allow independent error handling.
- Attachment metadata is embedded directly within the ticket detail payload returned by `GET /api/v1/tickets/:id`, removing the need for a separate standalone attachment metadata endpoint.
- File attachments are stored in local disk storage under the `/uploads` directory to simulate the development environment.
- Ticket Number format `TKT-YYYY-XXXXXX` is a project-level implementation decision intended to provide a human-readable and unique identifier.
- Backend validation is authoritative even when equivalent validation is performed on the frontend.
- Backend ownership checks are required for every ticket and attachment operation that exposes or modifies requester-owned data.
- If ticket creation succeeds but attachment upload fails, the ticket remains persisted and the user can retry the attachment operation from Ticket Detail.
- Uploaded filenames are sanitized before storage to prevent unsafe filesystem paths and path traversal.
- The detailed API request/response contracts are maintained in `docs/lab-02/api-spec.md`.
- The detailed UI, accessibility, responsive, and visual rules are maintained in `docs/lab-02/ui-spec.md`.
- The planned automated test scenarios and Acceptance-Criterion traceability are maintained in `docs/lab-02/tests.md`.
- The design is intentionally compatible with the authentication model planned for Lab 3 without implementing authentication in Lab 2.
